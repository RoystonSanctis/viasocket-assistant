# viaSocket Assistant config

Public, data-only configuration for the [viaSocket Assistant](https://github.com/RoystonSanctis/viasocket-assistant) Chrome extension. The extension downloads these files at runtime, so wording, prompts, selectors, providers and switches can change without publishing a new extension version. A copy of this folder is also bundled into every extension build as the last-resort fallback.

Nothing here is code. The extension never runs anything from here: it only reads JSON and Markdown and checks them against its own schemas.

## What each file controls

| File | Controls |
|---|---|
| `manifest.json` | Entry point. `configVersion`, `minExtensionVersion` and the path of every other file. |
| `providers.json` | AI providers on the options page: name, API style (`adapter`), key format, where to get a key, badges, setup tips, recommended models, on/off. |
| `selectors.json` | Where things are on the viaSocket page: the app hosts the mascot runs on (it can only narrow the hosts compiled into the extension, never add one; an empty list means all of them), CSS selectors for the canvas, step nodes, step panel, Save/Test/Publish buttons, Developer Hub sections, field labels, and floating widgets the mascot must not cover. |
| `mascot.json` | Bubble size, roaming, a colour per mood, fixed phrases (greeting, errors), and reactions to what the user does (test failed, flow published...). |
| `flags.json` | Limits (agent steps, tool result size, conversation length), default proactivity, Developer Hub and trigger tool switches, extra confirmations, run-data stripping, and the emergency off switch. |
| `tools.json` | Turn individual agent tools off, or override the description the AI sees. Tools themselves live in the extension. |
| `voice.json` | Speech-to-text models (Whisper, on device), the vocabulary transcripts are corrected towards, spoken-reply rate, pitch and length, and push-to-talk timing. |
| `prompts/system.md` | The assistant's persona and global rules. Sent with every request. |
| `prompts/flow-builder.md` | How to build and edit flows with the `vs_*` and `ui_*` tools. Added on flow pages. |
| `prompts/dev-hub.md` | How to build plugs with the `dh_*` tools. Added on Developer Hub pages. |
| `prompts/reactions.md` | Proactive behaviour and suggestion rules. |
| `schemas/` | JSON Schemas for every JSON file. Used by CI only; not shipped. |
| `scripts/validate.mjs` | The validator CI runs. |

Prompts may use these placeholders, which the extension fills in: `{{orgId}}`, `{{projectId}}`, `{{scriptId}}`, `{{pluginId}}`, `{{page}}`, `{{date}}`, `{{proactivity}}`. Keep tool names exactly as the extension defines them (`vs_add_step`, `dh_dry_run`, ...); `tools.json` lists them all.

## How the extension loads it

You edit this `config/` folder on the repo's `main` (or `beta`) branch. The **Config** GitHub Action validates it and publishes its contents to a channel branch, with the files at the branch root. The extension then reads `${CONFIG_REMOTE_BASE}/config-${channel}/manifest.json` and every file the manifest lists, for example `https://raw.githubusercontent.com/RoystonSanctis/viasocket-assistant/config-stable/manifest.json`. `CONFIG_REMOTE_BASE` and `CONFIG_BRANCH_PREFIX` are set in `extension/src/shared/constants.ts`.

- Every file is validated in the extension. If anything is invalid or unreachable, the extension keeps its last good config, and falls back to the copy bundled at build time.
- It re-checks every 10 minutes. Users can force a check with **Refresh config** on the options page, which also shows the active `configVersion`.
- `minExtensionVersion` declares the oldest extension a config is written for. Raise it when a change depends on a newer extension, so older installs keep the config they already have.

## Channels

| You push `config/` to | Published to | Who gets it |
|---|---|---|
| `main` | `config-stable` | Everyone, by default. |
| `beta` | `config-beta` | Users who choose the Beta channel on the options page. |

The `config-*` branches are regenerated by the Action on every publish: never edit them by hand.

Typical flow: open a pull request, merge it into `beta`, try it with the extension set to Beta, then merge `beta` into `main`. Protect `main` and `beta` and require the **Config / validate** check.

## Propagation

- `raw.githubusercontent.com` caches files for about 5 minutes, and the extension checks every 10 minutes, so allow up to about 15 minutes for a change to reach everyone.
- **Bump `configVersion` on every change** (convention `YYYY.MM.DD-N`). It is how a config is identified in the options page and in bug reports. CI warns when files changed but the version didn't.
- Files are cached one by one, so right after a change a client can combine a new manifest with an older file. After any download that changed the config, the extension downloads every file again (ignoring the ETag) on its following checks, until one made after the roughly 6-minute cache window comes back unchanged. A mixed config is therefore replaced at the first check after that window. Keep each change self-contained and backward compatible anyway. To rename a file, add the new file and point the manifest at it first, and delete the old one in a later change.

## Safety model

This repo is public and can change the assistant's behaviour for every user, so the extension limits what it can do:

- **Data only.** Chrome Web Store rules forbid remotely hosted code, and the extension never evaluates anything from here. Prompts are plain text sent to the AI.
- **Provider addresses are compiled in.** For built-in providers, the base URL comes from the extension code and any `baseUrl` here is ignored, so a change to this repo can never redirect a saved key.
- **Keys are bound to origins.** A key is sent only to the origin it was saved with. Only the `HTTP-Referer` and `X-Title` extra headers are ever sent; anything else is dropped.
- **Confirmations live in code.** Deleting, publishing, discarding and overwriting always ask the user, whatever the config says. `flags.alwaysConfirm` can add confirmations but never remove one. `tools.json` can switch tools off or reword them, but cannot add tools or change what they do.
- **Selectors only locate.** They are used to find elements to point at and to keep the mascot out of the way.
- **Kill switch.** `flags.disabled: true` (with an optional `disabledMessage`) turns the assistant off for everyone within minutes.

A compromised repo could still make the assistant give bad advice or behave oddly within those limits, so treat write access like a release key: require reviews, protect `main`, `beta` and the `config-*` branches (allow only the Action to push to `config-*`), and enforce 2FA for maintainers.

## Adding a provider

Each entry in `providers.json` needs an `id` (lowercase letters, digits and dashes), a `name` and an `adapter`:

- `openai`: any OpenAI-compatible Chat Completions API with tool calling.
- `anthropic`: the Anthropic Messages API.

Other fields: `keyPattern` (a regular expression for a basic format check), `keyPageUrl`, `validatePath` and `modelsPath` (appended to the base URL to check a key and list models), `noKey` for local servers, `badges`, `setupTip`, `recommendedModels`, `requires: ["tools"]` (the assistant needs tool calling), `extraHeaders` and `enabled`.

**Built-in providers** (`openrouter`, `groq`, `gemini`, `mistral`, `openai`, `anthropic`, `deepseek`, `ollama`, `lmstudio`) have their address compiled into the extension. Editing their entries changes what users see, not where keys go. To change a built-in address or make a new provider built in, change the extension (`src/background/llm/registry.ts`) and release it.

**Any other provider** needs a `baseUrl`. When a user saves a key for it, Chrome asks them to allow the extension to reach that origin, and the key is bound to it:

```json
{
  "id": "example-ai",
  "name": "Example AI",
  "adapter": "openai",
  "baseUrl": "https://api.example-ai.com/v1",
  "keyPageUrl": "https://example-ai.com/settings/keys",
  "modelsPath": "/models",
  "requires": ["tools"],
  "enabled": true
}
```

To hide a provider quickly, set `"enabled": false`.

## Fixing a broken selector

When viaSocket changes its UI, the mascot may stop finding a button or a step.

1. Open the page on `flow.viasocket.com` (and `beta-flow.viasocket.com`, which can render different UI), then find the element in DevTools.
2. Prefer `data-testid` attributes over classes. Scope to a container when a test id repeats (for example `[data-testid="step-config-slider"] [data-testid="save-button"]`).
3. Test it in the console: `document.querySelector('...')`. For `stepNode`, replace `{slugName}` with a real step name.
4. Edit `selectors.json`. Keep the key names: the extension looks them up by key. A comma-separated list works as a fallback; the first match in page order wins.
5. Bump `configVersion`, run the validator, merge to `beta`, check it with the Beta channel, then merge `beta` into `main`.

## Validate locally

```sh
cd config
npm ci
npm run validate        # or: node scripts/validate.mjs
```

The validator checks that every file the manifest lists exists and matches its schema, that prompts are non-empty and under 64 KB, that provider key patterns compile, that reaction highlights name real selector keys, that the default speech model exists, and that no API keys or private file paths slipped in. It warns when config files changed but `configVersion` did not.

## Optional: signed config (not implemented in the extension yet)

Signing would let the extension reject files that were not produced by your release process, even if the repo or the CDN were tampered with. A possible design:

1. Create an ECDSA P-256 key pair offline (`openssl ecparam -name prime256v1 -genkey -noout -out signing.pem`, then `openssl ec -in signing.pem -pubout -out signing.pub.pem`). Keep the private key in a protected GitHub Actions environment secret, or sign offline.
2. When publishing to `config-stable`, the workflow writes `signature.json` with the `configVersion`, the SHA-256 of `manifest.json` and of every file it lists, and an ECDSA signature over that list. WebCrypto expects the raw `r||s` signature form, not OpenSSL's DER, so convert it.
3. The extension would ship the public key, fetch `signature.json`, verify it with `crypto.subtle.verify`, check each file's hash, and keep its last good config when anything does not match.

Using a separate `signature.json` keeps the existing schemas unchanged; adding fields to `manifest.json` instead would also need a schema update.
